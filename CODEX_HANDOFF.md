## Mission

Turn the stock FXPAK Pro / sd2snes menu into a polished SNES-native frontend matching the established visual target: dark navy/black dashboard, SNES-purple accents, top navigation, large selected-game box art, title/metadata panel, favorites/recent/homebrew/hacks, clean footer button prompts, and smooth SNES-appropriate motion.

This is not a generic reskin. The target is a premium, artwork-driven console dashboard that still runs on original SNES hardware through the FXPAK Pro.

## Existing architecture discoveries

The menu is its own SNES ROM written primarily in 65C816 assembly under `snes/`.

The FXPAK MCU firmware lives under `src/` and handles directory scans, configuration, ROM loading, favorites/recent games, etc.

The menu already uses:

- BG1 + BG2
- OBJ/sprites
- Mode 3 / Mode 5 switching
- HDMA
- color math
- generated font tiles
- full 256-color CGRAM upload
- dirty/redraw state
- controller dispatch
- existing favorites/recent handling

Do not throw away these working primitives.

The upstream theme branch additionally supports custom logo, custom font, custom button graphics, palettes, gradient backgrounds, configurable selection bars, and arbitrary sprite placement.

## Non-negotiable safety rule

Preserve the known-good ROM-loading path and directory/MCU protocol while the frontend is being rebuilt.

Do not rewrite the entire file selector in one pass.

Prefer incremental integration:

1. Build and validate current `feature/fxpak-os`.
2. Fix only compile/link/runtime regressions introduced by our changes.
3. Keep ROM launching and directory traversal working.
4. Add graphical dashboard pieces around the proven loader.
5. Replace old UI sections only after the replacement is demonstrably functional.

## Original Phase 1 brief (completed)

### 1. Establish a reproducible menu build

The `snes/README` documents `snescom` / `sneslink` requirements. Install or build the required toolchain in the Codex environment.

From `snes/`, run `make` and produce:

- `menu.bin`
- `m3nu.bin`

Treat `m3nu.bin` as the primary FXPAK Pro Mk.III artifact.

If the current FXPAK OS commits do not compile, fix them with minimal changes and commit those fixes separately.

### 2. Test the menu ROM

Use an emulator capable of exercising the sd2snes menu where practical (the repo documents bsnes-plus support and related test configuration).

At minimum validate:

- boot reaches menu
- NMI remains stable
- no VRAM/CGRAM corruption
- existing file list still renders
- controller input still works
- directory traversal works
- ROM selection path is not broken
- FXPAK OS top/footer overlay appears

If emulator limitations prevent full validation, document exactly what was verified and what still needs real-hardware testing.

### 3. Make the first real artwork appear in the menu

Use `tools/fxpakos/compile_art.py` to generate a test cover asset.

Current first-pass cover format:

- 80x112 pixels
- 10x14 tiles
- SNES 4bpp planar data
- one 16-color BGR555 palette
- tilemap generated by the compiler

Goal: render one compiled cover image inside the running menu ROM without disturbing the existing loader.

Start with a static bundled test asset if loading dynamic SD-card artwork would force too many protocol changes at once.

Once a static cover is proven on-screen, design the cleanest path for loading selected-game art from SD/SRAM via the MCU.

## PC-side asset pipeline

Keep expensive work off the SNES whenever possible.

The long-term pipeline should scan a ROM library and prebuild:

- cover art
- screenshots
- metadata
- indexes
- favorites/recent helpers where appropriate
- SNES-native tile/palette data

The SNES frontend should consume prepared binary assets rather than decode PNG/JPEG.

Do not add web scraping to SNES-side code.
